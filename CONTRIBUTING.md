# Contributing

Thanks for taking an interest in **Repo Radar** — the tracker that keeps
[@mchittineni](https://github.com/mchittineni)'s repository dashboard fresh. This guide covers how
the project is laid out, how to run it locally, and what a good pull request looks like.

## Project layout

```
.
├── .github/workflows/status-update.yml   # scheduled job that refreshes the dashboard
├── data/
│   ├── repos.json                        # tracked repositories (generated by sync_repos.py)
│   ├── repo-metadata.json                # machine-readable export of the latest run
│   ├── repo-descriptions.json            # optional hand-written repository blurbs
│   └── repo_status.log                   # run log (git-ignored)
├── scripts/
│   ├── sync_repos.py                     # discovers repositories owned by the tracked account
│   ├── update_status.py                  # fetches stats and rewrites README.md
│   ├── cleanup_readme.py                 # de-duplicates repository blocks in README.md
│   ├── run.sh                            # convenience wrapper around the Python scripts
│   └── requirements.txt                  # runtime dependencies
└── README.md                             # generated dashboard (edit the generator, not this)
```

> [!IMPORTANT]
> Everything between `<!-- START_REPO_STATUS -->` and `<!-- END_REPO_STATUS -->` in `README.md` —
> plus the header above it — is generated. To change how the dashboard looks, edit the
> `generate_*` and `build_readme_header` functions in `scripts/update_status.py`, then re-run the
> script. Hand edits inside that block are overwritten on the next run.

## Local setup

See [INSTALLATION.md](INSTALLATION.md) for the full walkthrough. The short version:

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r scripts/requirements.txt
export GH_TOKEN=$(gh auth token)   # or a classic PAT with public_repo scope

python scripts/sync_repos.py --dry-run     # preview the tracked repository list
python scripts/update_status.py --sort stars
```

Optional but recommended:

```bash
pip install pre-commit
pre-commit install
```

## Making a change

1. **Branch** off `main`: `git switch -c feat/short-description`.
2. **Keep the scope tight.** One behavioural change per pull request.
3. **Run what you touched.** There is no test suite yet, so exercise the scripts directly and
   paste the relevant log lines into the pull request. At minimum:
   - `python scripts/sync_repos.py --dry-run`
   - `python scripts/update_status.py --sort stars`
   - `bash -n scripts/run.sh` after editing the shell wrapper
4. **Check the generated diff.** If your change touches the generator, include a snippet of the
   resulting `README.md` so reviewers can see the rendered effect.
5. **Do not commit secrets.** Tokens belong in `.env` (git-ignored) or repository secrets.

## What CI checks

Every pull request against `main` runs [`.github/workflows/pr-check.yml`](.github/workflows/pr-check.yml):

| Job | What it does |
|---|---|
| 🧹 **Lint** | `ruff check`, byte-compiles `scripts/`, and shellchecks `scripts/run.sh` |
| ✅ **Validate** | parses every workflow, issue form, JSON data file and `pyproject.toml`, then checks `data/repos.json` has no duplicates, every curated blurb points at a tracked repository, and `README.md` still has its generated-section markers |
| 🛰️ **Smoke** | runs the discovery in `--dry-run` mode and generates a dashboard into a scratch file, asserting one detail block per tracked repository and no leaked `None` values or unrendered placeholders |

The smoke job uses the built-in `GITHUB_TOKEN`, so it works on pull requests from
forks without any secret. It never writes to the repository copies of `README.md` or
`data/`.

Reproduce all three locally:

```bash
pip install ruff
ruff check .
python -m compileall -q scripts
shellcheck --severity=warning scripts/run.sh
python .github/scripts/validate_repo.py

export GH_TOKEN=$(gh auth token)
python scripts/update_status.py --sort stars --readme /tmp/README.generated.md
python .github/scripts/assert_dashboard.py /tmp/README.generated.md
```

A missing curated blurb is only a notice, not a failure — `sync_repos.py` can discover
a repository at any time and the generator falls back to its GitHub description. An
*orphan* blurb naming a repository that is no longer tracked does fail the build.

## Style

- **Python**: standard library first, `requests` for HTTP, type hints on function signatures, and a
  short docstring on every function. Keep the logging style that is already there
  (`logger.info` with the emoji-prefixed success lines).
- **Shell**: `bash`, `set -e`, quoted variable expansions, and paths resolved relative to the
  script so the wrapper works from any directory.
- **Markdown**: wrap prose at roughly 100 columns.
- **Line length**: 100 characters, enforced by `ruff` via pre-commit.

## Commit messages

This repository uses [Conventional Commits](https://www.conventionalcommits.org/). The automated
job commits as:

```
fix(git-tracker): auto-updated project status with latest changes [skip ci]
```

Follow the same shape for your own work:

```
feat(dashboard): add language mix pie chart
fix(sync): keep archived repositories out of repos.json
docs(installation): explain the GH_USERNAME repository variable
chore(deps): bump requests to 2.34.2
```

Common scopes: `dashboard`, `sync`, `workflow`, `docs`, `deps`, `git-tracker`.
